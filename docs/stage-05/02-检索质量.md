## 一步一步讲

### 因素1：分块太大/太小

- 太大：一段里混很多主题，检索不准  
- 太小：缺上下文，答案碎片化  

### 因素2：清洗与元数据

标题、来源、权限，都要保留。本仓库 `ChunkHit` 已带 `source` / `chunk_id`。

### 因素3：查询改写

用户问得很口语，检索词可能要改写得更「文档风」。

### 因素4：混合检索与重排（了解）

- 关键词检索：精确匹配强（本仓库词重叠就是简化版）  
- 向量检索：语义相近强  
- 二者结合 + rerank：更稳  

### 如何验收

准备「问题→应命中哪篇」，看 Recall@k。不要只看「回答是否流畅」。

## 打开代码一起看（在本仓库里做对比实验）

对照 `src/agent_lab/rag/__init__.py`：

### 1）打分公式就在 `search`

```python
overlap = len(q & tokens)           # 问题词 ∩ 段落词
score = overlap / max(1, len(q))  # 除以问题词数
```

改问题措辞（同义不同词）会导致命中变化——这就是「词法检索」的局限，也解释了为何业界要上向量。

### 2）`chunk_size` 从哪传进去

```python
index.add_document(doc_id, text, chunk_size=180)
```

演示脚本没暴露参数时，你可以改默认值或改 `stage05_rag_demo.py` 传入不同 `chunk_size`，对同一问题对比 `hits`。

### 3）迷你评测怎么接第9章思路

不必等第9章：手写 5 行

```text
问题 | 期望 source 含 rag_basics 或 tool_loop
```

跑完 search 看 `hits[0].source` 对不对——这就是 Recall@1 的手工版。

```powershell
python examples/stage05_rag_demo.py
```
