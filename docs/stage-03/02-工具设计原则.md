# 第3章第2节：工具设计原则（写给初学者）

## 写在前面

工具是 Agent 的手。  
手如果设计得含糊、危险、没超时，模型再聪明也会帮倒忙。

本节不写新大功能，只教你**怎么判断一个工具好不好**。

---

## 本节你将学会

1. 好工具的几条具体标准
2. 什么是副作用、为什么要分级
3. 什么是 HITL（人工确认）

---

## 先用一个生活例子：遥控器按钮

坏遥控器：一个按钮叫「搞定」，按下可能关机、可能删文件、可能在线购买。  
好遥控器：每个按钮名字清楚，危险操作要长按确认。

工具的 `name` / `description` / 参数说明，就是按钮上的字。

---

## 一步一步讲清楚

### 原则1：一件事一个工具

- 好：`search_docs`、`read_file`、`send_email_draft`
- 坏：`do_anything(command: str)`

### 原则2：描述要可执行

别写「处理数据」。  
要写「根据 expression 计算算术，支持 + - * /」。

### 原则3：输入要可校验

参数用 JSON Schema / Pydantic 约束。  
非法参数应返回可读错误，让模型有机会改。

### 原则4：必须能超时

网络工具没有超时 = 可能永久卡住整个 Agent。

### 原则5：错误要变成观察，不要直接让进程崩

Agent Loop 里应捕获工具异常，把 `ERROR: ...` 文本回给模型。

### 原则6：副作用分级

| 级别 | 例子 | 建议 |
|------|------|------|
| none（只读） | 搜索、读文档、计算 | 可自动 |
| write（可改数据） | 写文件、创建工单 | 谨慎，可确认 |
| irreversible（难撤销） | 转账、群发、删库 | 必须人工确认 |

### 原则7：HITL（Human-in-the-loop）

高危工具：`require_confirmation=True`  
没确认就返回「需要用户确认」，不要真执行。

## 打开代码一起看

打开 `src/agent_lab/tools/__init__.py` 与 `tools/builtin.py`。

### 1）设计字段落在 `ToolSpec`

```python
side_effect: Literal["none", "write", "irreversible"] = "none"
require_confirmation: bool = False
```

原则写在文档里不够：要写进类型，执行时才能强制检查。

### 2）确认门闩在 `execute` 开头

```python
if tool.spec.require_confirmation and not confirmed:
    return "ERROR: 该工具需要用户确认后才能执行。"
```

没确认 → **返回错误观察**，不是静默跳过，也不是直接抛崩。

### 3）内置三个工具的风险级别

看 `build_builtin_registry()`：`calculator` / `get_time` / `http_get` 都是只读向（`side_effect="none"` 或默认）。  
`http_get` 虽只读，仍有「出站网络」风险，所以正文练习要求你想域名白名单——生产里常在 handler 开头拦截。

## 常见卡点问答

**Q：工具是不是越多越好？**  
A：不是。太多模型选不过来。按任务逐步加。

**Q：描述写很长会不会更好？**  
A：清晰比长更重要。写清「何时用/何时不用/参数例子」。

## 本节小结

- 工具设计是 Agent 质量的一半
- 名称、描述、权限、超时、错误处理，缺一不可
