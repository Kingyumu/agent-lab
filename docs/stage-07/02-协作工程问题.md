# 第7章第2节：协作时最容易翻车的地方

## 写在前面

多 Agent 的坑，多半不是「模型不够聪明」，而是**治理缺失**。  
对照本仓库的最小 Pipeline，看哪些刹车还没装上——这比再堆一个角色更重要。

## 本节你将学会

1. 五类典型翻车点  
2. 每类在本仓库「现状 / 可补」对照  
3. 何时不该上多 Agent  

---

## 翻车点 ↔ 代码里可以怎么防

| 翻车点 | 症状 | 本仓库现状 | 你可以怎么加 |
|--------|------|------------|--------------|
| 停不下来 | 账单爆炸、互相抬杠 | Pipeline 固定 2 次 chat | 辩论循环必须读 `max_rounds` |
| 职责重叠 | 两人重复写同一段 | 两个不同 system | 交接改 JSON 字段契约 |
| 无共同事实 | Writer 胡编引用 | 只传 findings 字符串 | 共享 `workspace: dict`（检索、引用 id） |
| 权限过大 | 某角色误调高危工具 | 尚未分角色挂工具 | 每角色一个 `ToolRegistry` 白名单 |
| 看不懂是谁的错 | 只能看最终两段文本 | 无 per-agent trace | 每次 chat 打 `agent_name` 进日志 |

## 打开代码一起看（对照治理缺口）

重读 `ResearchWriterPipeline.run`（`src/agent_lab/multi_agent/pipeline.py`）。

### 1）有终止，但仍是「裸奔」

固定 2 步 = 天然有终止（Pipeline 优点）。  
但：没有 `run_id`、没有逐步耗时、没有「研究员输出是否为空」的校验。

### 2）Prompt 约束 ≠ 硬约束

Writer 的 system 写了「不要编造要点外事实」。  
若 findings 为空，Writer 仍可能编——应在代码层：

```python
if not findings.strip():
    return MultiAgentResult(research="", article="（中止）研究员无产出")
```

或接第6章 `verify_final_answer`。

### 3）`max_rounds` 是未接线的刹车

打开 `__init__` 确认：字段存在，`run` 未引用。  
练习：改成 while 辩论时，第一件事就是 `if round >= self.max_rounds: break`。

### 4）对比第3章已有的治理

`AgentLoop` 已有：`max_steps`、`StepTrace`、工具白名单、观察截断。  
多 Agent 应**继承同等治理**，而不是「多角色就免检」。

```powershell
python examples/stage07_multi_agent_demo.py --mock
```

在笔记画表：若加第三角色 Editor，消息如何传、何时停止、失败谁负责。

## 何时不该上多 Agent（抄进笔记）

1. 单次问答 / 单工具就能完成  
2. 步骤完全固定 → 用普通 Workflow 更稳  
3. 还没有单 Agent 评测集  
4. 团队还不会做权限与 trace  
5. 只是为了「看起来高级」
